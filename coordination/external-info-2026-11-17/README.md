## 3. 共用最小记录约定

### 标识与关联

- 保留现有 CPI `event_id`，不要重新编号。Agent 3 的 CPI 案例引用同一 ID。
- 新观察和事实 ID 各自加 `cpi-`、`muse-`、`prop-` 前缀，避免撞名。
- `event_id` 表示事件；`claim_id` 表示同一项事实断言；`version_id` 表示断言版本；`observation_id` 表示来源观察。
- 今天整理旧材料生成的 ID，注明 `catalogued_at`。今天计算的文件哈希不能冒充历史抓取时的哈希。
- `changes_kind` 使用 `initial / updates / corrects / retracts / confirms / unknown`。正常状态演变与纠错分开。

### 四种时间不得合并

| 字段 | 含义 |
|---|---|
| `source_published_at` | 来源声明的发布时间；另存原始时间文字和证据位置 |
| `source_updated_at` | 来源声明的更新时间，不等于采集者已收到 |
| `collector_seen_at` | 有证据支持的实际收到时间；旧 MD 自述与原始执行日志分级 |
| `extraction_completed_at` | 信息整理完成时间；不能倒填到历史事件时刻 |

已知时刻采用带时区的 ISO 8601，统一为 UTC。每个时间字段各自配 `time_metadata.<字段名>`，其中保存 `precision=second/minute/day/unknown`、`original_text`、`original_timezone`、`date_value` 和 `evidence_ref`，不能用一个精度代表整行。

仅知日期时，时间戳字段填 null，`date_value` 保存 `YYYY-MM-DD`，precision 为 day；不虚构零点或 UTC 时刻。完全未知则 precision 为 unknown，附 `missing_reason`，不可填 0、当前时间或推定的历史时刻。旧 `time_precision` 可保留兼容，但必须说明它具体描述哪个字段。CSV 中的 time_metadata 用 JSON 字符串编码。

`availability_mode`：

- `LIVE_OBSERVED`：有当时采集日志/响应等证据，能够支持收到时点。
- `HISTORICALLY_DOCUMENTED`：现在回查到的历史公告或其他公开资料。
- `RETROSPECTIVE_ONLY`：事后整理或回忆，不能证明当时系统已知；沿用原研究接口名称。

另记 `evidence_origin`：如 `official_archive`、`source_page`、`contemporaneous_capture`、`collector_log`、`document_assertion`、`secondary_report`。历史文章可以有可证的发布时间，但仍不代表本采集系统当时收到。`LIVE_OBSERVED` 不是本轮交付的必过门槛；正确标记历史证据即可。

未来计算模型可用时点时，不能早于实际收到与整理完成；当前只补资料，不把缺失的收到时点补成公告时间。

### 去重与解释

- 同 URL、同内容反复查询，不增加独立报道数；保留查询回执与首次/末次观测。
- 同 URL 内容发生变化，建立版本；不同网站转载同一根源消息，增加传播入口，不增加独立事实证据。
- 时间相近、措辞相似不必然证明转载关系；无法确定根源时标 `unknown`。
- 原文事实、来源的观点、整理者解释分栏。价格表现可保存在 `market_reaction_text`，不得混入纯外部事实特征。
- 找到的最早材料仅是“本次检索范围内最早找到”，不是全网首发证明。

## 4. 交付、状态与并行上传

每个执行者只写自己的输出目录。首批文件放 `v1/`；已发布交付不覆盖，修复新增 `v2/` 并记录父版本与差异。任务根目录的 `STATUS.md` 可更新，其他旧文件保留。

`STATUS.md` 至少包含：任务 ID、负责人、状态、实际输入提交、最新交付目录、完成项、缺失项、下一步、UTC 更新时间。状态用 `TODO / IN_PROGRESS / READY_FOR_REVIEW / BLOCKED`。已完成但仍含如实说明的历史缺口，可以交 `READY_FOR_REVIEW`，不必为了清空未知而停工。

每个 `vN/` 都交 `manifest.json`：任务 ID、输入仓库/分支/提交、所用路径及文件哈希、检索时间范围、输出文件及 SHA-256、与上一版的差异、已知缺口、测试结果。哈希清单不包含 manifest 自身，避免自引用。输出提交 SHA 在交付消息中返回，不要求把提交自身的 SHA 写进同一次提交。

上传规则：

1. 开工先读本 README、自己的任务书和最新分支头。
2. 不修改根 README、原始 `intel/`、原 CPI 文件、其他执行者目录或这套任务书。
3. 推荐向 `main` 提交自己目录的增量。提交前重新读取分支头，保留他人新增文件。
4. API 提交必须基于现有完整 tree；更新分支需校验预期旧 SHA，不强推。分支前进时重新检查差异后再提交。
5. 用本地 Git 时只提交明确属于自己的路径；不覆盖工作区，不执行强制重置、整库替换或强推。
6. 如果已有独立分支，返回准确分支、提交和文件链接；不要自行合并其他人的分支。无上传权限就提供成果并标“尚未上传”，不可声称已交付。

## 5. 共同验收与后续顺序

- 文件可解析、ID 唯一、外键可追、UTC 与时间精度一致。
- 数值、单位、初版/修订版、来源时间/收到时间区分清楚。
- CSV 与 JSONL 共用字段逐项一致；空值编码方式明确。
- 缺失资料有具体范围与原因，结论强度不超过证据。
- 旧资产保持原样；没有上传密钥、账户配置、私人记录或大段受版权保护全文。

验收顺序：Agent 1 可先进入历史公告时钟连接测试；Agent 2 验收来源/版本接口；Agent 3 验收传播链。某项未齐不阻止其他项完成。通过接口验收后，再另行预注册更大样本与行情连接研究。

六次公告、5–10 条观察、两个案例只是接口测试集，不是统计有效性或交易胜率的证明。本轮不改研究候选、不改冻结 B0、不下真实或模拟订单、不恢复或新增自动轮询，不以等待新数据替代现有历史资料整理。
